# Preview基本編集エラーのTDD調査・修正計画

## 1. 目的

Previewでファイルを編集中に、文字の入力・削除・改行によってエラーが発生したり、
本文、カーソル位置、保存結果が期待と異なったりする問題を、再現条件を曖昧にせず
TDDで修正するための計画を定める。

この文書の段階では原因を決めつけず、実装も変更しない。まずユーザーが実際に行う操作を
実Chromium上の失敗テストとして固定し、その失敗を証拠としてから仕様と実装を変更する。

## 2. 完了条件

次のすべてを満たしたときに修正完了とする。

1. 報告された操作を、修正前のコードで安定して失敗させられる。
2. エラーの有無だけでなく、画面上の本文、Markdownモデル、カーソル位置を検証する。
3. 必要なら保存後のディスク内容と、タブを開き直した後の内容も検証する。
4. 最小修正後に新しい回帰テストが成功する。
5. 関連する既存の編集、IME、利用フローテストも成功する。
6. CursorへVSIXを再インストールし、同じ操作を実画面でも確認する。

## 3. 最初に記録する再現情報

「期待通りではない」だけでは誤った仕様をテストにしてしまうため、各不具合を次の形式で
1ケースずつ記録する。入力・削除・改行は原因が異なる可能性があるため、最初から1件に
まとめない。

| 項目         | 記録例                                                |
| ---------- | -------------------------------------------------- |
| モード        | Preview / Raw                                      |
| ブロック種別     | 通常段落、見出し、箇条書き、チェックボックス、引用、コード、表セル                  |
| 初期Markdown | `- [ ] abc` のように全文を記録                              |
| カーソル・選択    | 行頭、途中、末尾、範囲選択あり                                    |
| 操作         | `x`を入力、Backspace、Delete、Enter、Shift+Enter、日本語IME確定 |
| 期待結果       | 操作後のMarkdown全文と期待カーソル位置                            |
| 実際の結果      | 欠落、重複、別行へ移動、エラー表示など                                |
| 発生頻度       | 毎回、連打時のみ、約N回に1回                                    |
| タイミング      | ファイルを開いた直後、保存中、外部更新直後など                            |
| 証拠         | エラーメッセージ、Developer Toolsのスタック、画面録画                 |

特に次の条件差を残す。

- 半角英数字と日本語IME入力
- 1文字入力と連続入力
- 空行、行頭、行中、行末
- 通常段落と構造ブロック
- 単発操作と、入力→削除→Enter→Undoの連続操作
- 新規ファイルと既存ファイル
- Previewを開いた直後と、しばらく編集した後

## 5. TDDの必須手順

### Phase 0: 再現条件を1つに固定する

最も頻繁に起きる1ケースを選び、初期Markdown、カーソル位置、操作、期待Markdownを固定する。
最初は入力・削除・改行のうち1操作だけにする。複合操作でしか発生しない場合も、操作を
1つずつ減らして最小シーケンスを探す。

### Phase 1: REDテストを書く

実Chromiumテストで、実際のキー入力を行う。実装関数を直接呼び出すだけのテストにはしない。
最低限、次の4点を検証する。

1. 操作前の本文とカーソルが再現条件どおりである。
2. 操作中にpage errorまたは未処理例外が発生していない。
3. 操作後の `h.model()` が期待Markdownと一致する。
4. 操作後のProseMirror selectionが期待位置にある。

保存問題の疑いがある場合は、変更通知の内容と開き直した内容も追加する。

テストタイトルは仕様文にする。

```text
通常段落の行中で文字を入力すると、前後の文字を失わずカーソルが入力直後に残る
通常段落の行末でBackspaceすると、直前の1文字だけが削除される
通常段落の途中でEnterすると、カーソル位置で2段落に分割される
```

### Phase 2: 修正前に失敗を確認する

```bash
npm run build:webview
npm run test:browser
```

調査中はMochaのgrepで新しいテストだけに絞ってよい。最終確認ではカテゴリ全体を実行する。

失敗時に残す証拠:

- 期待値と実値のMarkdown全文
- selectionの `from` / `to` と親ノード種別
- page errorのメッセージとスタック
- 必要ならスクリーンショット
- 発生が確率的なら、試行回数と何回目で失敗したか

テストが最初から成功した場合は実装修正へ進まない。カーソル位置、ブロック種別、IME、
入力速度、選択状態、ビューポート幅、保存タイミングのどれが不足しているかを再調査する。

### Phase 3: 仕様を記録する

RED確認後、`docs/specifications/` に対象バグの仕様書を作る。少なくとも以下を記録する。

- 症状と最小再現
- 期待動作
- REDテスト名と失敗内容
- 判明した原因
- 採用する修正と、採用しなかった案
- 回帰テストの対応関係

同時に `docs/specifications/spec-test-coverage.md` を更新する。

### Phase 4: 最小の実装修正を行う

失敗を成功に変えるために必要な最小箇所だけを変更する。入力、削除、改行を一括で
書き換えず、共通原因がテストとスタックから証明できた場合だけ共通処理を修正する。

主な確認観点:

- キーイベントを複数プラグインが二重処理していないか
- transactionをdispatchした後に古いstate/selectionを使っていないか
- DOMをProseMirror管理外から直接変更していないか
- decoration/widgetが編集可能領域へ混入していないか
- serializerとparserの往復で空白・改行・記法が変形していないか
- hostへの変更通知と外部更新のechoが競合していないか
- composition中のkeydownを通常入力として処理していないか

`src/preview/webview/` を変更したら、テスト前に必ずバンドルを更新する。

```bash
npm run build:webview
```

### Phase 5: GREENと回帰確認

確認順序は次のとおり。

```bash
# 1. 新しい失敗テスト
npm run test:browser

# 2. 高速な下位テストも追加した場合
npm run test:unit

# 3. 保存・ホスト連携を変更した場合
npm test

# 4. 型、Lint、全ビルド
npm run lint:error
npm run compile

# 5. テストカタログ更新
npm run docs:test-catalog
```

確率的なレースだった場合は、該当テストを最低5回連続で実行する。retryで失敗を隠さず、
1回でも落ちたら未修正として扱う。

### Phase 6: Cursor実機確認

テストがGREENになった後だけVSIXを作成・再インストールする。

```bash
npm run package
cursor --install-extension "./ipreview-$(node -p "require('./package.json').version").vsix" --force
cursor --list-extensions --show-versions | rg '^ipreview\.ipreview@'
```

Cursorで `Developer: Reload Window` を実行し、REDテストと同じ初期Markdown・カーソル位置・
操作で確認する。目視だけで別シナリオを試して「直った」と判定しない。

## 6. 最初に作るテストマトリクス

一度に全組み合わせを実装せず、まず通常段落の3ケースをP0としてREDにする。その後、
実際の報告条件に合わせて構造ブロックとIMEへ広げる。

| 優先度 | 初期状態     | 操作                    | 必須アサーション          |
| --- | -------- | --------------------- | ----------------- |
| P0  | 通常段落の行中  | 半角1文字入力               | 本文、selection、例外なし |
| P0  | 通常段落の行末  | Backspace             | 1文字だけ削除、selection |
| P0  | 通常段落の行中  | Enter                 | 2段落への分割、selection |
| P1  | 空段落      | 連続入力→削除→再入力           | 欠落・重複なし、Undo可能    |
| P1  | 見出し・箇条書き | 入力、Backspace、Enter    | 記法と本文、selection   |
| P1  | チェックボックス | Enter、項目削除            | 次項目の状態、Markdown   |
| P1  | 表セル      | 入力、Delete、Enter       | セル内容、表構造、直列化      |
| P1  | コードブロック  | 入力、Backspace、Enter    | フェンスと本文の保持        |
| P2  | 日本語IME   | 変換確定、確定直後Enter        | 重複・欠落なし、改行1回      |
| P2  | 長文の連続操作  | 入力→削除→Enter→Undo/Redo | 全文、selection、履歴   |

P0の通常段落がすべて壊れるなら初期化、共通キーマップ、同期処理を優先して調べる。
通常段落は正常で特定ブロックだけ壊れるなら、そのブロック固有プラグインへ範囲を絞る。

## 7. 追加するテストの共通仕様

以下のテストIDをテスト名の先頭に付ける。既存テストが同じ操作を扱っていても、下記の
必須アサーションをすべて満たさない場合は「部分的にカバー」とし、不足分を既存テストへ追加する。
同じ内容のテストを重複して作らない。

### 7.1 全browserテストのアサーション契約

各操作の直後に、原則として次の順で確認する。`textContent` だけではブロック境界やMarkdown
記法の破損を検出できないため、1種類の値だけで合否を決めない。

1. `h.errors` が空であり、`pageerror`、未処理Promise rejection、consoleのerrorがない。
2. `h.docText()` が期待する表示本文と厳密一致する。文字の欠落、重複、順序逆転を許容しない。
3. `h.model()` の `topTypes` と `outline` が期待するProseMirror構造と一致する。
4. `h.lastChangeMarkdown()` が期待Markdown全文と一致する。末尾改行の仕様差は事前に固定し、
   テスト側で安易に `trim()` しない。
5. `selFrom === selTo` であるべきケースでは選択がcollapseしており、`selParentText` と
   ブロック内オフセットが期待位置に一致する。絶対位置だけでなく「入力した文字の直後」などの
   意味的な位置も確認する。
6. 操作前後で無関係な前後ブロック、mark、list itemの `checked`、表の行列数が不変である。
7. 非同期の変更通知が落ち着いた後も同じ値である。固定sleepではなく、期待するchange通知または
   モデル状態を待つ。

この契約を実装できるよう、必要なら `PreviewHandle` に次の観測APIを先に追加する。

- `selection()`：`from`、`to`、empty、親ノード型、親内オフセット、選択テキスト
- `changeMessages()`：全change通知のMarkdownと順序（最終値だけで競合を隠さない）
- `consoleErrors`：`console.error` と未処理rejection
- `waitForMarkdown(expected)`：ポーリングで期待する直列化結果を待つ
- `dispatchComposition(...)`：CDPを使った composition start/update/commit/cancel

### 7.2 キー操作の原則

- 再現テストは `page.keyboard.type/press` またはCDP IME操作を使い、transactionを直接生成しない。
- カーソル配置は事前条件の安定化に限ってモデルAPIを使ってよい。操作対象のキー自体は実キーにする。
- macOS用の `Meta+z` だけに固定せず、テストヘルパーで実行OSに応じたUndo/Redoキーを使う。
- 1文字ずつの中間状態が重要なケースでは、各文字入力後に本文、Markdown、selectionを確認する。
- `waitForTimeout` は履歴グループ境界など時間そのものが仕様である場合だけ使う。

## 8. 具体的に追加・補強するテスト

`<caret>` はカーソル、`[text]` は選択範囲を表す記法であり、実際のMarkdownには含めない。
各ケースで初期化直後の状態も確認してから操作する。

本章は2種類のテストを含む。8.1〜8.6は今回の不具合調査で先に実装するP0/P1であり、
8.7以降は入力編集全体を守るための拡充プログラムである。8.7以降は個々のバグ修正の
ブロッカーにしない（10章のゲート区分を参照）。未実装分は
`docs/specifications/preview-usage-flow-test-backlog.md` でIDごとに管理し、
テスト化したらバックログから消してカタログへ移す。

### 8.1 P0: 通常段落の入力・削除・改行

| ID       | 初期Markdownと位置             | 実操作           | 期待結果と必須確認                                                                   |
| -------- | ------------------------- | ------------- | --------------------------------------------------------------------------- |
| EDIT-001 | `abc<caret>def\n\nTAIL\n` | `X`           | Markdownは `abcXdef\n\nTAIL\n`。カーソルはX直後。TAIL不変。changeは最終的に同じ全文を1回以上通知し、例外なし。 |
| EDIT-002 | `<caret>abcdef\n\nTAIL\n` | `X`           | `Xabcdef`。先頭境界で前ブロックへ移動せずX直後に残る。                                            |
| EDIT-003 | `abcdef<caret>\n\nTAIL\n` | `X`           | `abcdefX`。末尾やTAILへ文字が混入しない。                                                 |
| EDIT-004 | `abc<caret>def`           | `XYZ`を1文字ずつ入力 | 中間値が順に `abcXdef`、`abcXYdef`、`abcXYZdef`。全段階でカーソルは入力直後、欠落・重複なし。              |
| EDIT-005 | `abc<caret>def`           | Backspace     | `abdef`。直前の`c`だけ削除しカーソルは`b`直後。                                              |
| EDIT-006 | `abc<caret>def`           | Delete        | `abcef`。直後の`d`だけ削除しカーソル位置は不変。                                               |
| EDIT-007 | `<caret>abc`              | Backspace     | 文書、構造、カーソルが変わらず例外なし。                                                        |
| EDIT-008 | `abc<caret>`              | Delete        | 文書、構造、カーソルが変わらず例外なし。                                                        |
| EDIT-009 | `abc<caret>def\n\nTAIL\n` | Enter         | `abc\n\ndef\n\nTAIL\n` となり、カーソルは後半段落の先頭。topTypesはparagraph 3個。              |
| EDIT-010 | `abc<caret>\n\nTAIL\n`    | Enter         | 現行仕様がhardbreakならoutlineにhardbreakが1個だけで、カーソルは改行直後。段落分割仕様へ変更するなら先に仕様書を更新する。  |
| EDIT-011 | `<caret>abc`              | Enter         | 空の前半と`abc`の後半を保持。serializerが空ブロックを消さず、カーソルは`abc`側の先頭。                       |
| EDIT-012 | `abc<caret>def`           | Shift+Enter   | hardbreakを1個だけ作り、段落ノードは分割しない。直列化結果とカーソルが改行直後。                               |

EDIT-009とEDIT-010は既存テストの期待仕様と矛盾し得るため、REDを書く前に
`previewKeymapPlugin.ts` と既存の `editingOperations.test.ts` が定めるEnter仕様を照合する。
ユーザー操作として「Enter=段落分割」「Enter=hardbreak」のどちらを採るかを1つに統一し、
同じ位置で両方を期待するテストは残さない。

**採用結果（`7d0e907` で決定・以降のセッションで確認）**: 「Enter=hardbreak」を採用した
（EDIT-010: 通常段落の途中/先頭/末尾でのEnterは常にhardbreak、段落分割はしない）。
ただしこの決定だけでは、hardbreakで継続している行に見出し/リスト/チェックボックス等の
Markdown記法を続けてタイプしても自動変換されない（`customInputRules`がテキストブロック
全体基準でマッチ判定するため）という広範囲の副作用があり、`hardbreak-line-markdown-
conversion-fix.md` で別途対応した（`hardbreakLineInputRulesPlugin`が、既定でマッチしない
場合のみhardbreak境界を本物の段落分割にしてから既存のinput ruleを適用する）。

### 8.3 P1: ブロック境界と構造ブロック

### 8.26 テストケース生成の組み合わせ規則

すべての直積は膨大になるため、無作為に減らさず、次の軸でpairwiseを生成し、重要境界だけは
全組み合わせを明示テストにする。生成時のseedと選ばれたケース名を失敗ログへ出す。

| 軸    | 値                                                                           |
| ---- | --------------------------------------------------------------------------- |
| ブロック | paragraph、H1〜H6、bullet、ordered、task false/true、quote、code、table header/body |
| 項目位置 | 文書先頭/中間/末尾、list先頭/中間/末尾、nested                                              |
| カーソル | marker前/中/直後、本文先頭/途中/末尾、空ブロック                                               |
| 操作   | type、IME、Enter、Shift+Enter、Backspace、Delete、paste、Undo/Redo                 |
| 選択   | collapsed、forward、backward、同一block、複数block、AllSelection、CellSelection       |
| 前要素  | なし、同種、paragraph、異種、空block、table/code                                        |
| 次要素  | なし、同種、paragraph、異種、空block、table/code                                        |
| 速度   | 単発、文字間50ms、高速、key repeat                                                    |
| 同期状態 | idle、save中、external push直後、Raw切替直前、background復帰直後                           |
| 表示   | focus syntax on/off、wrap有/無、狭い/広いviewport                                   |
| 文字種  | ASCII、日本語IME、空白、記号、emoji、RTL、結合文字                                           |

必ず全組み合わせにする境界は次のとおり。

- 全ブロック種別 × 本文先頭/途中/末尾 × type/Backspace/Delete/Enter
- H1〜H6 × marker前/中/直後 × type/Backspace/Delete
- bullet/ordered/task × 先頭/中間/末尾/空項目 × Enter/Backspace/Delete
- task false/true × 次要素task/bullet/paragraph/なし × 行末Delete
- ASCII/IME/emoji × paragraph/heading/task/table/code × 入力/削除/Undo
- idle/save中/external push直後 × 高速入力/Enter/Raw切替

### 8.28 各ヘルパーの責務と禁止事項

| 責務（実装先）                                     | 内容                                   | 禁止事項                               |
| ------------------------------------------- | ------------------------------------ | ---------------------------------- |
| selection作成（inputEditingDrivers.ts）         | モデル位置、mouse、keyboardによるselection作成   | 操作対象キーまでtransactionで代用しない          |
| キー入力（inputEditingDrivers.ts）                | OS別shortcut、key repeat、文字間隔          | テストごとに`Meta`を直書きしない                |
| IME操作（inputEditingDrivers.ts）               | CDP composition開始/更新/確定/cancel       | `keyboard.type('日本語')`をIMEテストと呼ばない |
| clipboard操作（inputEditingDrivers.ts）         | MIME別paste、cut/copy、drag data        | 期待Markdownを生成しない                   |
| モデル観測（previewBrowserHarness.ts）             | doc、outline、selection、node attrs取得   | DOM textだけでモデルを推測しない               |
| message観測（previewBrowserHarness.ts）         | change/external/initの全順序を記録          | 最後のmessageだけ残して中間破損を隠さない           |
| エラー観測（previewBrowserHarness.ts）             | pageerror、console.error、rejection    | 既知エラーを無条件filterしない                 |
| 状態待機（previewBrowserHarness.ts）              | 条件成立までpoll、timeout診断                 | 固定sleepを汎用待機にしない                   |
| 共通assert（inputEditingAssertions.ts）         | 本文、構造、Markdown、selectionの共通assert    | 実装コードと同じ変換関数で期待値を作らない              |
| ケース列挙（inputEditingCases.ts）                 | ブロック×位置×操作の列挙、pairwise生成             | 対象外を黙ってskipしない                     |
| failure artifact（inputEditingAssertions.ts） | diff、selection、message列、screenshot保存 | 成功時に巨大artifactを残さない                |

### 8.29 fixture作成規則

- fixtureの先頭や末尾へテスト都合の`TAIL`を置く場合、それ自体が期待Markdownに含まれることを明記する。
- カーソル記号`<caret>`と選択記号`[selection]`はfixtureファイルへ直接保存せず、case定義側で位置を指定する。
- initialとexpectedは別ファイルにし、expectedを実装serializerで自動生成しない。
- 末尾改行、空行数、半角/全角空白を見える形で診断できるdiffを使う。
- 1 fixtureは原則1目的とする。複合fixtureは`flows/`だけに置く。
- 実ユーザー文書や秘密情報をfixtureへコピーしない。
- 10KB、100KB、1MB級の性能fixtureは生成scriptで決定的に作り、巨大ファイルを不用意にcommitしない。
- malformed fixtureはformatterをかけず、壊れた状態が意図的である旨を先頭コメントまたは隣接READMEへ記録する。

├── expected.md
├── actual-model.md

├── selection-after.json

`environment.json`にはOS、Node、Cursor、Electron/Chromium、拡張version、commit SHA、設定、viewport、
実行seedを含める。成功時は通常artifactを保存せず、CIの容量を圧迫しない。

### 8.31 実装単位と実行時間の層分け

| 層      | 内容                                     | 目標時間      | 実行タイミング                   |
| ------ | -------------------------------------- | --------- | ------------------------- |
| Smoke  | CHAR-001、EDIT P0、HEAD/LIST/TASK代表、保存1件 | 2分以内      | 各commit前                  |
| Core   | 全ブロック×基本操作、IME代表、clipboard             | 10分以内     | PRごと                      |
| Full   | 本書の全決定的ケース                             | 30分以内     | merge前                    |
| Race   | RACE全件を10〜100反復                        | 60分以内     | merge前/nightly            |
| Stress | 大文書、長時間、leak、1000操作                    | 時間上限を個別設定 | nightly/release candidate |
| VSIX実機 | REAL代表、保存/切替/再起動                       | 手動記録      | release前                  |

時間短縮のためにassertionを減らさない。fixture共有、browser context再利用、下位層への切り出しで
短縮する。ただし状態漏れを検出するlong-sessionテスト以外は、各testのdoc、selection、message列を
独立させる。

### 8.32 実装進捗

| 日付         | 対象                    | 状態    | 実装・確認内容                                                                                                              |
| ---------- | --------------------- | ----- | -------------------------------------------------------------------------------------------------------------------- |
| 2026-07-13 | EDIT-001〜010、EDIT-012 | 完全カバー | `test/browser/editing-core/plainTextEditing.test.ts`。実Chromiumで11件GREEN。本文、構造、selection、host送信Markdown、page errorを確認 |
| 2026-07-13 | EDIT-011              | 未実装   | 空段落先頭のEnterについて、空行保持pluginを含む期待Markdownを確定して追加する                                                                     |
| 2026-07-13 | 共通観測API               | 一部実装  | `ModelSnapshot`へselection詳細、`consoleErrors`、`changeMessages()`、`waitForMarkdown()`を追加                                |

最初のRED実行では、Backspace/Delete/Shift+Enterのモデル変更後にchangeが見えず失敗した。
調査の結果、製品の通知欠落ではなく、Milkdown listenerの200ms debounceに対してハーネスの

`waitForMarkdown()`へ変更した。通常入力11件は製品修正なしでGREENとなったため、既存仕様の
回帰固定として扱う。

## 9. テスト実装の順序と既存テストの棚卸し

1. 上記IDを `未実装 / 部分カバー / 完全カバー / 対象外（理由）` の4状態で一覧化する。

## 10. リリース判定ゲート

ゲートは2段に分ける。10.1は対象バグを修正するたびに毎回満たす条件、10.2は8.7以降の
テスト拡充プログラム全体の完了条件であり、個々のバグ修正のブロッカーにはしない。
10.2の進捗は `preview-usage-flow-test-backlog.md` と `spec-test-coverage.md` で管理する。

### 10.1 対象バグ修正のリリース条件（毎回必須）

- 対象不具合のRED証拠があり、その同じテストが修正後にGREENである。
- P0全件と、変更した実装に関係するP1全件がskipなしで成功する。ブラウザ未導入によるskipを
  成功扱いにしないCIジョブを1つ以上用意する。

- 新規テストだけでなく `npm run test:browser`、`npm run test:unit`、`npm test`、
  `npm run lint:error`、`npm run compile` がすべて終了コード0になる。

- レース・IME・同期に触れた修正では、該当テストが同一ビルドで10回連続成功する。retryなし、
  失敗0件、未説明のskip 0件である。

- page error、console error、未処理rejectionが0件であり、テスト終了後に開いたpage、browser、
  VS Code editor、タイマーが残らない。

- `npm run docs:test-catalog` 実行後のカタログに新規テストが掲載され、仕様書のテストIDと対応する。
- VSIXを新規生成して強制再インストールし、対象バグのテストIDと、代表としてEDIT-001/005/006/009を
  Cursor実機で同じfixture・同じカーソル位置から確認する。IME・保存に触れた修正では
  IME-001/002、SYNC-002/005も加える。

- リリース候補VSIXのversionとインストール後versionが一致し、以前のbundleを見ていないことを確認する。
- CHANGELOGへ症状、影響範囲、修正内容、追加した回帰テストを記録する。

### 10.2 テスト拡充プログラム全体の完了条件（個別修正のブロッカーにしない）

## 11. 失敗時の切り分け基準

| 観測結果                        | 最初に疑う範囲                                                   |
| --------------------------- | --------------------------------------------------------- |
| `docText`の時点で不正             | keymap、input rule、composition、selection mapping           |
| モデルは正しいがMarkdown通知だけ不正      | serializer、change listener、debounce                       |
| browserは正しいがTextDocumentが不正 | `previewPanel.ts`、version管理、編集適用queue                     |
| TextDocumentは正しいがディスクだけ不正   | save/defer、URI、外部更新競合                                     |
| 本文は正しいがselectionだけ不正        | transaction mapping、focus syntax decoration、external echo |
| 単発は成功し連続操作だけ失敗              | stale state、二重dispatch、非同期順序、履歴group                      |
| ASCIIは成功しIMEだけ失敗            | `isComposing`判定、composition中keydown、確定直後Enter guard       |

失敗を見つけたら、期待値を実装に合わせて緩めない。まず最小fixtureまで縮小し、テストID、seed、
操作列、全change通知、selection、スタックを保存する。仕様が誤っていたと判明した場合だけ、理由を
本書または個別仕様書へ記録して期待値を変更する。

## 12. やらないこと

- RED確認前に実装を変更しない。
- jsdomテストが成功しただけで実ブラウザの不具合を修正済みにしない。
- 「例外が出ない」だけで成功とせず、本文とカーソルも検証する。
- 固定の長いsleepや無条件retryでレースを隠さない。
- 入力・削除・改行・IMEを根拠なく一度に大改修しない。
- 実装をコピーしたテストだけで実ソースを検証したことにしない。
- Cursorへの再インストールをテストより先に行わない。
